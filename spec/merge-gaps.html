Blockers — contradictions that stop implementation

B1"Merge current into selected" end-state is self-contradictoryBlocker
Spec says (merge.md:41)
checkout selected branch → merge previous branch into current branch → stay in current branch
Issue

Once you check out the selected branch, "current branch" is the selected branch. So "merge previous into current" + "stay in current" lands you on the selected branch — but a user naturally expects to end where they started. Worse: if the merge conflicts mid-flow, you're now sitting on the selected branch with an in-progress conflicted merge, and the spec gives no recovery path.

Proposed resolution

Define the final state explicitly. Recommended: finish on the selected branch (that's the branch the user chose to advance), and say so in the modal copy ("You will switch to feature").

On conflict during the reverse direction, drop into the existing conflict flow (merging state + conflict.rs) on the selected branch, and make AbortMerge restore the pre-flow branch. Spell out that a clean checkout of the selected branch is a precondition (covered by B3's uncommitted check).

B2"Auto-commit if clean" doesn't map cleanly to git's defaultsBlocker
Spec says (merge.md:42–43)
The user is presented with a checkbox to auto-commit the merge if it's clean. The checkbox is enabled by default.
Issue

git merge already auto-commits a clean non-fast-forward merge. So the checkbox's two states need an explicit mapping, and two cases are unaddressed:

  • Fast-forward merge — produces no merge commit at all, so "auto-commit" is meaningless. Hide/disable the checkbox? Undefined.
  • Reverse direction (B1) — "clean → auto-commit" interacts with the extra checkout dance.
Proposed resolution

Map it concretely: checked → plain git merge <branch> (git commits the clean merge). Unchecked → git merge --no-commit <branch>, leaving the result staged for the user to review/commit via the existing commit box.

For a fast-forward, the checkbox is a no-op — keep it visible but note it only affects merge commits, or grey it out when the pre-check determines the merge will fast-forward.

B3"Uncommitted changes" — definition conflicts with code & glossaryBlocker
Spec says (merge.md:15, 35)
A check is made for uncommitted changes. If there are any, the user is presented with a warning and the flow exits without continuing.
Issue — three separate conflicts
  • Behavior change vs. today. ops::checkout uses libgit2 .safe() (ops.rs:695), which only refuses when changes would be overwritten; git otherwise carries clean changes across. The spec's "block on any uncommitted change" is a brand-new pre-flight check, not existing behavior.
  • Definition gap vs. code. The existing dirty flag is !staged.is_empty() || !unstaged.is_empty() (sidebar.rs) — it ignores untracked files and dirty submodules.
  • Glossary mismatch. context.md defines "uncommitted changes" as staged + unstaged + dirty submodules, and its Checkout-Flow example says the flow prompts to stash or discard. The spec offers neither — only "go commit it yourself."
Proposed resolution

Adopt the glossary definition verbatim: the check fails on staged, unstaged, or dirty submodules (decide explicitly on untracked — recommend ignoring untracked, as git does, since they never block a checkout/merge unless overwritten).

Reconcile the exit options with the glossary: either (a) update context.md to drop the stash/discard wording so "commit only" is canonical, or (b) extend the spec to offer stash/discard. Given the submodule-heavy workflow, the dirty-submodule case is the one most likely to bite — make it a first-class part of the check.

Gaps — undefined behavior to pin down

G1Conflict pre-check mechanism & post-merge resolution pathGap
Spec says (merge.md:44–46)
Both choices are checked for eligibility first. Will there be merge conflicts? Warning to the user on the files that contain conflicts.
Issue

Two omissions: (1) how conflicts are predicted (a git merge-tree dry-run? a trial --no-commit merge then abort?), and (2) what happens when the user proceeds and conflicts actually occur. The codebase already has the full machinery — merging state, per-file resolution in conflict.rs, and AbortMerge — but the spec never says the merge flow hands off to it.

Proposed resolution

Predict with git merge-tree (no working-tree mutation, fits the worker model and the "heads-up before you enter a conflict" intent). State that on an actual conflicted merge the flow transitions into the existing conflict-resolution flow (sets merging, surfaces ChangeKind::Conflicted files, routes to conflict.rs), and that AbortMerge is the escape hatch.

G2"Pull latest" for a non-checked-out, diverged local branchGap
Spec says (merge.md:57–63)
When checked, the selected branch is brought up to its upstream's latest before the merge.
Issue

You can't git pull a branch you're not on. Bringing a non-current local branch to its upstream is a fetch + ref update, which only works if the branch fast-forwards to upstream. The spec ignores the diverged case — ahead > 0 && behind > 0 — where the local branch has its own commits and upstream has new ones. That's the most likely real scenario and there's no defined behavior.

Proposed resolution

Scope "pull latest" to fast-forwardable only (behind > 0 && ahead == 0): fetch, then git branch -f <branch> <upstream>. When the branch has diverged (ahead > 0 && behind > 0), do not offer the checkbox — show it disabled with a note ("local branch has diverged from upstream; merge its current tip or reconcile it first"). Never force-update a diverged branch silently — that's data loss. The snapshot already carries BranchInfo.ahead/behind, so the UI can decide without extra I/O.

G3Async eligibility checks — modal loading state undefinedGap
Issue

Three eligibility checks need I/O off the UI thread: the remote-merge fetch (merge.md:54), the upstream-changes probe (merge.md:63), and the conflict pre-check (merge.md:45). The spec says checks happen "first" but never says what the modal shows while they run, or whether the user can act before they complete. With the worker/Job architecture these are all async round-trips.

Proposed resolution

Define the modal's loading state: open immediately, show a spinner/"checking…" line, and keep the action buttons disabled until the probe Update returns. The conflict warning and the pull-latest checkbox populate in place when their results arrive. This matches the existing one-job-one-update contract.

G4Worker contract: Job::Merge can't carry the new optionsGap
Issue

The existing variant is Job::Merge { id, branch } (mod.rs:92). The new flow needs to express: direction (into-current vs. into-selected), auto-commit, pull-latest, and fetch-first (remote source). None fit today's variant. The spec doesn't have to design the enum, but it should acknowledge the merge job now carries direction + flags so the contract change is on the radar.

Proposed resolution

Note in the spec that the merge job gains: direction, auto_commit: bool, pull_latest: bool, and a fetch-first step for remote sources. Add a separate conflict-probe job (or fold it into the modal's open sequence) so the pre-check has its own Update. Keep each job → exactly one Update, per the architecture invariant.

G5Merge-in-progress guard silently droppedGap
Issue

Today the old dialog disables SWITCH/MERGE while tab.merging.is_some(). The new Checkout Flow only checks "uncommitted changes" — but a repo mid-merge isn't necessarily dirty in the staged/unstaged sense, so the guard is lost. Checking out (or starting a new merge) on top of an in-progress merge is undefined.

Proposed resolution

Add an explicit precondition to both flows: if a merge is already in progress (RepositoryState::Merge), block with a warning to finish or abort it first. This preserves the guard the discarded dialog provided.

Minor — smaller omissions

M1Submodule update after checkout/mergeMinor

Checkout/merge can move submodule pointers, and there's an existing UpdateSubmodules job. The spec is silent on whether the flows auto-update submodules. Leaving them stale shows as "dirty submodules" (per the glossary), which would then block the next flow (B3) — a trap, given the submodule-heavy workflow.

Resolution: state whether checkout/merge auto-runs submodule update on success, or deliberately leaves it manual. Recommend auto-update after a successful checkout/merge to avoid the self-blocking trap.

M2No-op / fast-forward / already-merged messagingMinor

Merging an already-up-to-date or already-merged branch ("Already up to date"), and the fast-forward case, have no defined messaging.

Resolution: surface git's "Already up to date" verbatim, and label fast-forward results distinctly from merge-commit results so the user understands no merge commit was created.

M3Error messaging for non-conflict failuresMinor

Non-conflict merge failures (e.g. the reverse-direction checkout failing) fall into the generic error path with no spec'd message.

Resolution: pass git's stderr through to the existing Acted error surface; no bespoke copy needed, but say that's the intent.

M4Modal icon glyph & double-click on current branchMinor

The "icon on the right to show it opens a modal" (merge.md:30) doesn't name a glyph — these live in theme.rs; don't hardcode. Separately, double-clicking the current/HEAD branch is presumably a no-op (today guarded by !b.is_head) but isn't stated.

Resolution: pick a glyph from theme.rs and reference it by name; confirm in the spec that double-clicking the HEAD branch is a no-op.

Unresolved questions

  3. "Pull latest" when the local branch has diverged from upstream — refuse, force, or merge-first?
  4. Does an in-progress merge block the Checkout Flow?
  5. Should checkout/merge auto-run submodule update afterward?
